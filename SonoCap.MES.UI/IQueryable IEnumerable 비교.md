# 📌 `IQueryable<T>` vs `IEnumerable<T>` 비교 정리

| 항목        | `IQueryable<T>`                                   | `IEnumerable<T>`                                 |
|-------------|----------------------------------------------------|--------------------------------------------------|
| **실행 시점** | 지연 실행 (쿼리 생성 후 DB에서 실행됨)              | 즉시 실행 (메모리 내에서 바로 실행됨)              |
| **대상**     | DB, 외부 쿼리 가능한 데이터소스 (`EF`, `LINQ to SQL` 등) | 메모리에 존재하는 컬렉션 (`List<T>`, `Array`)     |
| **장점**     | 조건 필터링, 정렬, 페이징 등을 **DB에서 처리 가능** → 성능 우수 | 로직이 단순하며 메모리에서 안전하게 조작 가능     |
| **단점**     | 복잡한 쿼리 작성 시 성능/유지보수 이슈 발생 가능        | 데이터 양이 많으면 **전체 메모리 로드로 인해 느림** |

---

## ✅ 사용 용도 요약

| 상황                                            | 적합한 타입        | 이유                                           |
|--------------------------------------------------|---------------------|------------------------------------------------|
| DB에서 조건 걸고 가져올 때                        | `IQueryable<T>`     | SQL로 변환되어 DB에서 필터링, 정렬 가능         |
| 메모리에 이미 올라온 데이터에 대해 필터링할 때      | `IEnumerable<T>`    | LINQ 연산을 C# 메모리 내부에서 실행             |
| `.Take()`, `.Skip()` 등 페이징 처리 필요할 때     | `IQueryable<T>`     | SQL `OFFSET` / `FETCH` 등으로 최적화 가능       |
| 리스트 전체를 한 번에 가져온 뒤 로직 처리할 때      | `IEnumerable<T>`    | 불필요한 DB 접속 없이 바로 처리 가능            |
| `foreach`, `.ToList()` 등 즉시 반복 처리할 때      | `IEnumerable<T>`    | 이미 메모리에 있음 → 바로 처리 가능             |

---

## 🧠 결론 정리

- **DB 쿼리 기반이면 → `IQueryable<T>`**  
  → 조건, 정렬, 페이징을 **DB에서 처리**하고, 필요한 데이터만 가져오는 게 성능상 유리

- **이미 메모리에 있는 데이터라면 → `IEnumerable<T>`**  
  → **불필요한 DB 접근 없이** LINQ 연산으로 간단하게 조작 가능

---

> 💡 보너스 팁:  
> `IQueryable`을 `ToList()`, `First()`, `Count()` 등으로 끝내는 순간 → DB 쿼리 실행됨
